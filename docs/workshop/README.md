# Facilitate the controlled release workshop

This 90-minute workshop follows one catalog ranking change through a hosted release.
Participants practice explaining why a deployment, exposure, recovery or completion
decision is justified. One authorized operator controls the shared lab; participants
inspect evidence and complete the [worksheet](participant-worksheet.md).

Use the [tutorial](../tutorial/README.md) as the walkthrough and the
[answer key](answer-key.md) privately for facilitation. Read the
[Build 5 acceptance record](../build-05-closeout.md) before presenting this format
as rehearsed. Do not describe a proposed agenda as observed timing.

## Prepare before the session

- Complete [operator setup](../tutorial/setup.md) and obtain the concrete hosted
  authorization and traffic budget. Set up a separate operator and facilitator
  if available; only approved identities may act. The clean hosted acceptance run
  is independent and untimed, not replaced by this session.
- Prepare the source/review/provenance history and a secret-free evidence packet
  using the [index](../tutorial/evidence.md). Include the actual failed and uncertain
  records. Participants must not need access to the author's account or local paths.
- Prepare E/off in staging and live, verify its native rollback target, and reserve
  the complete sequence and recovery budget. Preserve the current operator state.
  Refresh stale off evidence through approved observation, not a redeployment.
- Keep the current operator checkout apart from the local F/G source-repair checkout.
  Queue no speculative mutations. Inspect automatically queued staging internal
  requests instead of creating duplicates.
- Ask participants to open the worksheet and prepared evidence. Do not distribute
  release tokens. Give any live catalog browsing a counted allowance; all other
  participant inspection uses the downloaded evidence packet.

## Run of show

The tutorial remains available for complete commands. The facilitator introduces
what each action will establish before the operator starts it. Use waiting time
for participants to inspect the previous proof, without launching another writer.

| Minutes | Facilitation and operator action | Participant output |
|---|---|---|
| 0–10 | Introduce the read-only catalog and prepared E baseline. Explain source, immutable image, deployed instance, and feature audience. | Checkpoint 1: identify the subject and what readiness cannot prove. |
| 10–20 | Inspect the disclosed F fixture, original reviews/builds, and provenance. Demonstrate wrong-subject refusal without deployment. | Checkpoint 2: separate provenance, functional checks and runtime performance. |
| 20–35 | Stage F and verify normal-query treatment; promote the same digest with live off; start internal then limited exposure as ready. | Checkpoint 3: distinguish deployment from exposure using actual records. |
| 35–55 | Observe F's challenge failure and refused expansion; independently disable the flag and verify original behavior on F. | Checkpoint 4: identify the failed gate, denied action, and recovery evidence. |
| 55–65 | Perform native E rollback and separate read-only reconciliation, retaining the original unknown result. | Checkpoint 5: compare the two independent recoveries. |
| 65–80 | Inspect/reproduce the local source repair as time permits; stage G's challenge, promote and follow the healthy rollout chain. | Trace each G stage to its own authorized predecessor; flag any missing step. |
| 80–90 | Inspect completion and separate monitoring, retain the flag and recovery targets, name the operating owner. | Checkpoint 6: submit an evidence-backed handoff and remaining obligations. |

Seventy minutes are allocated to deployment through handoff. Do not spend that
time rebuilding infrastructure or waiting for new image publication. The source
repair demonstration reuses PR #13's test and fix; G is the previously signed image.

## Handle delays without changing the lesson's claims

At each agenda boundary, check whether the hosted operation completed and its proof
is available. If not, say: “This operation is still pending. The next record is from
the September 2026 exercise.” Show the labeled historical packet for the next
teaching segment and mark that segment **recorded**, not live or newly verified.

Do not shorten observation windows, extend policy deadlines, bypass approvals,
change sampling, race writers, or rerun failed mutations to meet the agenda.
The authorized operator must still track any in-flight effect and finish the
necessary recovery safely, even if teaching has moved to recorded evidence.
Do not start a new hosted segment until its prerequisites and budget are satisfied.

If the intended F latency failure is replaced by an unexpected error or incomplete
window, keep it as the actual result. Use the historical latency diagnostic to
explain that teaching case while separately investigating the new failure.
A recorded fallback preserves teaching continuity; it cannot pass hosted acceptance.

## Review participant work and record actual timing

Use the [answer key](answer-key.md) to mark each checkpoint as supported, incomplete,
or contradicted, with a short evidence reference. Ask participants to repair an
unsupported decision. Report the number of submitted and supported checkpoints
only when those submissions exist. Attendance and a completed demo do not prove
learning, adoption or business impact.

For the timed rehearsal, record start/end for each segment, actual operator and
facilitator, docs SHA, live versus recorded delivery, approval/provider wait time,
questions, author interventions, and unfinished work. Keep proposed timings and
observed timings in separate columns. Feed instruction defects back into the
package and record verification of the correction in Build 5's acceptance record.

End by naming Nnenna as the operating owner, showing the actual final state, and
explaining daily signed monitoring, archive retention, the open CI/502 follow-ups,
and the separately reviewed criteria for eventual flag removal.
